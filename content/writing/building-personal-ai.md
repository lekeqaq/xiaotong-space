## 先整理知识，再开始问答

一个个人 AI 助手的价值，不在于它能聊多少话题，而在于能否准确回答与我有关的问题。项目背景、技术决策和实践笔记，才是它真正需要理解的内容。

这里记录知识库的设计思路。截至 2026 年 10 月，本站用 Nuxt Content 管理项目手记，技术文章则通过公开接口读取已发布快照。检索、向量索引和模型问答仍处于规划阶段，接入方案需要继续验证。

## 先把已有内容的边界理清楚

本站目前公开两个项目手记和三篇技术笔记。项目记录说明采用的方案与职责，技术笔记包含实现示例和后续设想。这两类内容需要保留各自的语境：写在笔记里的建议，并不自动代表项目已经实现了这项能力。

比如「声伴」手记明确记录了 LiveTalking、本地语言模型和讯飞语音服务的集成，也把流式输出、打断处理和弱网恢复列为待验证方向。如果助手只截取“打断处理”几个字，就可能把计划误读成成果。回答这类问题时，应同时取回能力说明与状态说明。

## Markdown 是内容的起点

项目手记维护在仓库的 Markdown 文件中，通过 Nuxt Content 在构建时校验和读取。技术文章同样以 Markdown 表达正文，但草稿与发布版本分开保存；公开页面只读取已发布快照，服务端解析正文并生成目录和代码高亮。仓库中的文章文件用于初始化内容，不代表运行时文章的唯一来源。

```ts
// 当前站点的文章列表只请求公开摘要，不下载正文或草稿。
const { data: articles } = await useWritingSummaries()

// 阅读某篇文章时，再获取已发布正文。
const { data: article } = await useFetch(`/api/content/articles/${slug}`)
```

公开摘要用于首页、文章列表和阅读导航；正文按需读取。每篇已发布文章既是可读页面，也是之后检索系统的知识来源。

## 发布规则也应成为检索规则

站点的首页、文章列表、详情、RSS 和 sitemap 只读取已发布内容，草稿不进入公开内容。这给知识库提供了一个明确的来源边界：未来建索引时，也应只读取已发布内容。

早期方案把所有内容放在 Markdown 与 Git 中，发布时需要重新构建。现在文章已经支持浏览器编辑与即时发布：发布会生成独立快照，保存草稿不会改变公开页面；项目手记仍随构建更新。这两条更新路径需要分别记录，不能把早期的静态方案当作当前实现。

公开文章接口每次读取当前发布状态，不使用持久化的浏览器缓存。服务端仅按正文版本复用 Markdown 解析结果；使用解析缓存之前仍检查文章是否已发布。因此修改后重新发布会使用新版本，撤回后下一次读取返回 404，RSS 和 sitemap 也不再包含该文章。已经打开的页面会在重新访问或刷新后更新。

页面展示与索引还需要使用同一份内容版本。文章修改或撤回后，应替换或删除对应片段；仅仅追加新向量，会让旧说法继续出现在回答里。文章的 `path` 与 `updated` 可以用于定位来源和判断更新，但具体同步机制仍需要实现。

## 分块需要保留上下文

固定字符数切块很容易把解释与代码分开。更适合技术文章的方式是先按标题拆分，再为较长章节设置上限。每个片段记录原文路径、章节标题和更新时间。

这些元数据不只用于检索，也用于把答案链接回原文。访客应该能够检查模型的回答，而不是只能相信它。

::content-callout{title="一个小原则"}
如果一段答案找不到明确来源，就先不要把它当成可靠的个人知识。
::

## 检索与生成分开评估

回答错误可能来自检索不到相关内容，也可能来自模型误读了已有片段。分别记录检索结果与最终答案，才能确定需要优化哪一层。

可以先用本站内容准备这样一个小型评估集。下面是待验证的预期行为，还没有实际运行结果：

| 问题                         | 应取回的来源                         | 预期行为                                  |
| ---------------------------- | ------------------------------------ | ----------------------------------------- |
| 逃个周末包含哪些部分？       | 项目手记“四个部分，一条产品链路”     | 回答小程序、API、后台和官网，并链接该章节 |
| 声伴的语音合成在本地运行吗？ | 项目手记“本地模型与语音服务各司其职” | 区分本地语言模型与讯飞 TTS 服务           |
| 声伴已经支持打断了吗？       | 项目手记“实时体验取决于整条链路”     | 说明这是待验证方向                        |
| 项目的实际响应延迟是多少？   | 现有资料没有测量值                   | 说明缺少测量记录，不生成数字              |

先检查是否检索到正确章节，再检查答案是否准确、状态是否清楚、引用是否能打开。这样可以区分“没有找对资料”和“读到了资料但理解错了”，让下一轮调整有具体依据。

## 给不确定性留出位置

对于缺少资料的问题，回答“目前的笔记没有提到”比猜一个看似合理的答案更好。个人助手不是万能的人设，而是已有内容的另一种阅读方式。

> 先让知识可靠，再让对话自然。

## 下一步

继续补充真实的项目记录，先用上面的评估问题验证按标题分块与关键词检索，再比较是否需要向量检索。模型接入之后，仍需验证回答中的引用、状态区分和缺少来源时的反馈。

现有站点测试覆盖文章渲染、RSS、sitemap 等内容出口；知识库接入后，还需要单独增加检索与回答评估。两者检查的对象不同，网页能正确展示文章，并不等于助手能准确使用文章。
