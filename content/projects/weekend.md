## 从「想出去走走」开始

周末只有两天，做攻略却可能花掉一个晚上。目的地、交通、预算、天气，每个选择都要来回查。逃个周末从一个具体的需求出发：给定出发地和出行条件，先找到值得去的地方，再整理成可以查看、调整和保存的两日行程。

我把它做成了一个包含微信小程序、业务 API、运营后台和品牌官网的项目。小程序承接实际规划流程，API 组织业务与 AI 任务，后台提供运营和排查入口，官网负责介绍产品与引导访问。

## 从条件到行程的使用路径

1. **表达出行条件。** 输入出发地、日期、交通方式、预算和兴趣，也可以补充特殊需求。
2. **比较目的地。** 创建推荐任务，等待结果，查看目的地及相关信息，再决定去哪里。
3. **生成两日行程。** 围绕选定目的地组织每天的安排，展示路线、地图、预算、天气和风险提示。
4. **把计划留在自己手里。** 查询历史行程，收藏、复制、调整或重新生成，也可以提交反馈。

这条路径里，生成结果只是中间一步。任务等待、失败恢复和后续管理同样是产品体验的一部分。

## 四个部分，一条产品链路

| 部分       | 承担的工作                                             | 技术选择                                    |
| ---------- | ------------------------------------------------------ | ------------------------------------------- |
| 微信小程序 | 出行条件、推荐结果、行程详情与个人旅行管理             | uni-app、Vue 3、TypeScript、Pinia           |
| 业务 API   | 鉴权、推荐与行程任务、数据存储、地图和天气集成         | FastAPI、Pydantic、SQLAlchemy、MySQL、Redis |
| 运营后台   | 用户与行程查询、失败任务处理、反馈、模型配置和权限管理 | Vue 3、Vite、Element Plus                   |
| 品牌官网   | 产品介绍、周末灵感、SEO 与小程序访问引导               | Nuxt 4、SSG、SCSS                           |

小程序通过统一的 Service 层访问接口，跨页数据与任务状态交给 Store；API 按路由、业务服务、数据访问和外部集成分层。四个部分分别维护，但对推荐条件、行程结构与任务状态使用一致的契约。

## 把「等 AI」变成明确的任务状态

推荐和行程生成都采用「创建任务 → 轮询状态 → 获取结果」的方式。前端根据 `pending / running / succeeded / failed` 展示进度、结果或失败入口，而不是让用户一直面对一个没有解释的加载动画。

这种拆分也让排查有了入口：一次生成对应一个任务，后台可以查看失败任务与 AI 调用记录。超时、失败和重试需要前后端一起处理，不能只靠前端重新点一次按钮。

## AI 组织内容，外部数据补充事实

模型接入层支持 DeepSeek 与 Ollama，负责根据条件生成结构化推荐和行程。返回内容经过 Schema 与业务校验后，再交给页面使用。

地图与地点信息接入高德，天气接入 Open-Meteo。代码中会用天气服务的结果补充目的地信息，用地图服务丰富地点与路线；这些信息不应只靠模型猜测。外部服务是否可用、数据是否足够，也会影响一次规划的完整程度。

对前端来说，结构化结果比一整段回答更有用：每天的安排、地点、预算与提示都有各自的位置，才能进一步支持地图展示和行程管理。

## 不止把结果展示出来

运营后台接入业务 API 的管理接口，覆盖用户、行程、任务、反馈、内容和模型配置。角色与按钮权限负责界面入口，服务端鉴权负责操作边界，审计记录帮助追踪处理过程。

官网则选择静态生成：让产品说明和访问入口可以直接被阅读和检索。官网中的推荐展示是本地演示，真正的推荐与行程任务留在小程序和 API 的业务链路中。

## 这次实践留下的认识

做 AI 产品，难点不只有生成内容，还包括输入约束、结构校验、等待体验、失败恢复，以及生成之后的管理。把这些环节连起来，才是一条完整的使用路径。
