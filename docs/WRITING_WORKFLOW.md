# Writing 内容维护

Writing 已通过 Nuxt Content 从 Markdown 读取文章。新增笔记只增加内容文件，列表、分类、搜索、详情、目录、RSS 与 sitemap 会随构建更新，不需要改 Vue 或 TypeScript。

## 现在就能用的方式

用 Obsidian、Typora 或其他 Markdown 编辑器打开本项目的 `content/writing/` 目录，像写普通笔记一样创建文章。Obsidian 中建议使用普通 Markdown 链接，而不是双链语法；图片放进项目的 `public/images/writing/`，按下面的路径引用。

例如创建 `content/writing/my-first-note.md`：

```markdown
---
title: '我的第一篇实践笔记'
description: '一句话说明这篇笔记记录了什么。'
date: '2026-10-06'
cover: '/images/personal/notebook.jpg'
tags: ['Vue', '实践']
category: 'Engineering'
draft: true
featured: false
readingTime: 3
---

## 从一个问题开始

在这里写正文。

![界面截图](/images/writing/my-screenshot.png)
```

- 文件名决定地址，例如 `/writing/my-first-note`。发布后尽量不要改文件名。
- 日期使用 `YYYY-MM-DD`，更新文章时可以补充 `updated`。
- 标题与摘要应说明文章是实现记录、设计思路还是概念整理。正文分别说明已经实现、尚待验证的部分；遇到的问题、调试过程与性能数据只使用实际记录。
- `draft: true` 不进入列表、详情、RSS 或 sitemap；准备发布时改为 `false`。
- `cover`、`tags`、`category`、`readingTime` 是当前内容 Schema 必填字段。
- `readingTime` 当前手动填写，不会自动计算。
- `category` 可写已有分类，也可创建新分类；列表会从文章内容中生成分类。
- 正文从二级标题开始，页面已经使用文章标题作为 H1。
- 图片引用使用 `/images/...`，不含 `public`。上面截图路径是示例，需要先放入真实图片。

本地保存后开发服务器会更新内容。已部署的静态站点需要重新生成和发布；写入本机文件不会自动更新线上网站。若使用 SSR 部署，也需要重新构建，使内容索引更新。

## 把实践写具体

写实现记录时，可以按“问题 → 约束 → 选择 → 验证 → 后续”组织正文。说明触发问题的场景、采用方案的原因和代价，并给出能核对的代码、命令或结果。没有运行记录时，将验证方法列为待办，避免把预期结果写成已经验证的结论。

设计笔记也可以用现有项目举例，但需要明确示例与完成状态。比如语音打断的设计可以解释过期响应、取消请求与播放队列的关系；项目是否已经支持打断，则以项目手记的实际实现说明为准。

## 更适合长期使用的方案

如果你想要“打开浏览器 → 新建笔记 → 上传图片 → 预览 → 发布”，推荐下一步接入 Git 驱动的可视化 CMS，例如 Decap CMS，让编辑器写入现有 Markdown 和图片目录，继续由 Nuxt Content 渲染。

接入前需根据实际仓库与部署平台确定登录方式、Git 授权和发布触发方式，再配置字段与图片目录。当前项目尚未接入该编辑器，也未配置自动发布。

建议的交付范围：

1. 仅作者可登录的管理入口。
2. 对应当前 Schema 的文章表单与正文编辑器。
3. 封面和正文图片上传。
4. 草稿保存、预览、发布和编辑已有笔记。
5. Git 提交触发构建部署，反馈发布状态。

不要只增加一个前端“保存”按钮或使用浏览器 localStorage 充当发布系统。内容必须持久保存，并能进入当前站点的构建流程。

## 什么时候需要独立后端

个人写作与项目记录，Git CMS 通常已经足够。只有需要多人角色权限、审核流、定时发布、评论、复杂内容查询或不经过构建的即时更新时，再考虑带数据库的 CMS，例如 Directus 或 Strapi。

这时需要同时设计鉴权、媒体存储、备份、内容 API、预览和缓存失效；接入 CMS API 也会改变当前 Markdown 内容链路。不要为了方便新增一篇笔记，先维护一整套自建后台。
